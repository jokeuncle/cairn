# Shared CLI, offline lexical queries and lossless text: development screen

Date: 2026-10-25. The product now has a read-only CLI and explicit cached lexical retrieval. Both tasks passed in every arm (10 sessions), but the preselected lexical/text candidate failed the cost gate. Commercial superiority and broad generalization remain unproven.

## Implemented and qualified

- `docsgraph query tool NAME JSON --repo ROOT`: the actual product CLI and MCP share transport-neutral dispatch. No external link-expansion prototype was merged. JSON/hybrid defaults remain unchanged.
- Explicit lexical mode uses cached source/BM25/structure without constructing a query provider or reading vector entries. An existing index and metadata are still needed; this does not eliminate indexing/summaries/storage. Cached reads also need no query provider.
- Optional text output retains every JSON value, source body, citation, warning and recovery hint. Repeated metadata may share columns/rows; multiline strings are verbatim length-delimited records. A decoder roundtrips them, and a compact-JSON fallback prevents increased UTF-8 size. This is not a tokenizer guarantee.
- Complete suite: 584 passed (five existing PDF binding deprecation warnings); Ruff clean; mypy clean for 73 source files including the materializer. Built wheel installed separately: all 72 product Python source files identical. Both modes called successfully inside the actual read-only/network-restricted Codex sandbox.

## Frozen real-Agent comparison

Codex CLI 0.164.0, gpt-6.1-sol/high; ten fresh sessions, serial. Two reused development tasktexts: Pydantic2.13.4 normalized ingestion module (28 independent checks) and Typer0.26.7 stateful release CLI (11 checks). Full module/source-access/requirements/citations reviewed independently before acceptance. Resilient callbacks were manually audited. Positive references and four seeded regressions qualified the runtime oracle.

Each task crosses hybrid/lexical and JSON/text, plus a fresh actual raw-document shell control. Primary candidate **lexical-text** was fixed before any model answer. Opaque workspace names, fixed rotated order, same model/permissions, 24 observed tool-invocation and 900-second budgets. Valid parameter/test errors are retained; no failed session was rerun.

I is cumulative input, K cached input, U=I−K, O all output including reasoning. Command invocations are not model turns.

Primary lexical/text vs raw: input_tokens +98.09%, uncached_input_tokens +21.67%, output_tokens -18.95%. It fails the predeclared no-regression and componentwise I/U/O gate; all answers being correct does not change this.

Hybrid/text is a **secondary exploratory observation**: input_tokens +22.97%, uncached_input_tokens -24.59%, output_tokens -2.80%. It also fails the price-independent componentwise gate because I rises. It is not retroactively substituted as the primary winner.

With uncached-input price normalized to 1, cached-input ratio r and output ratio q, cost C=U+rK+qO. Hybrid/text minus raw is `−18128 + 101632r − 367q`; lexical/text minus raw is `15981 + 340608r − 2480q`. Neither result is a universal paid-price advantage. No provider billing rate is assumed.

## What the traces establish

Fifteen earlier complete tool results roundtrip: compact JSON 82,342 bytes → text 77,683 bytes (-5.66%). This precedes the new Agent answers and measures serialization only. Every completed documentation CLI response in this screen also parsed; all attempts, including seven invalid-argument responses, remain in the records.

Skill reads vary substantially: hybrid/text has one process-skill command across two tasks, hybrid/JSON four, lexical/text five, raw one. Source retrieval, local test strategy and correction steps also differ. These are real end-to-end costs, but one observation per cell cannot isolate the causal effect of retrieval mode or serialization.

The seven CLI argument errors involve explicit evidence-only budgets used with another view. Error envelopes are preserved. Keyword search also currently exposes the section head rather than a matched-position excerpt; that is an identified usability limitation, not an improvement already tested here.

## Corpus, indexing and limits

Pydantic pinned `cf67d4b3193c3fe43ede18612ed62785eee11382`, seven selected documents; Typer pinned `4e10334990db4e7e1e9a71aff363bcae7f7fc76d`, nine selected documents. Typer sources were prepared by the actual delivered materializer (37 local Python includes), and all arms read identical expanded documents. Thus this phase tests the materializer→index→real Agent→executable module path.

The actual stock windowed OpenAI-compatible embedder was used for both document and query; Nomic768 at the local endpoint, UTF-8 window1500, **no injected query/document task prefix**. Summaries are controlled extractive summaries, and the embedding server was already running. This differs from earlier protocol adapters: results are not pooled with those studies and do not establish best-case dense-model quality or default LLM-summary startup cost.
- pydantic: 192,386 source bytes; 1,364,135 index bytes (7.09×); initial indexing 4.00s with warm model server.
- typer: 42,879 source bytes; 512,598 index bytes (11.95×); initial indexing 0.89s with warm model server.

Retain lexical retrieval for its independently verified endpoint-free query capability; leave modes/text opt-in. Do not market the failed primary cost candidate as commercially cheaper. A separate cross-project confirmation may test the secondary hybrid/text observation with new tasks and frozen criteria.
